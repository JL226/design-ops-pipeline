# 決策紀錄 · Decision log

每一條都是上線之後才被迫想清楚的。順序按撞到的時間。

---

## 1. 三段之間用檔案交換，不直接呼叫

**問題**：產生設計的那一側跑在不同的執行環境，沒有寫入試算表的權限；而且它建立的檔案，擁有權會算在觸發它的個人帳號上——那表示**離職或換帳號時，整批成品會跟著消失**。

**做法**：那一側只「出清單」，把任務寫成 JSON 丟進共用資料夾；另一側用服務帳號的身分讀清單、**真正把檔案生出來**。容量與擁有權才會落在正確的帳號。

**代價**：多一層非同步，除錯變難（狀態要從兩邊的日誌拼）。換來的是擁有權正確，而那是不能事後補救的。

> Stage handoff goes through JSON task files in a shared folder rather than direct calls — the generating side has no spreadsheet write access, and file ownership must land on the service account, not whoever triggered it.

## 2. 一輪的煞車是時間，不是檔案數

**問題**：改成「一個品項寫一個任務檔」之後，一輪產生的檔案數比舊版的單一大檔多十幾倍。上限設太小 → 交換區持續積壓 → 下游看不到狀態變化 → **每輪重複匯出同一批**。

**做法**：檔案數上限保留（防止單輪失控），但真正的煞車是 `MAX_RUNTIME_MS = 4.5 分鐘`——平台上限是 6 分鐘，留 1.5 分鐘給收尾寫回。

**為什麼**：檔案數是**代理指標**，實際耗時取決於每個檔案要下載幾張圖。用代理指標當煞車，會在「每個檔案都很重」的那天失效，而那正是最需要煞車的時候。

## 3. 找列用資料夾 ID，不用 SKU 文字

**問題**：SKU 會被改名（改錯字、改命名規則）。用文字比對的話，改名等於斷線。

**斷線的症狀是什麼**：它會**靜靜地新增一列**，沒有任何錯誤訊息。表上出現兩列同一個品項，而且兩列的狀態都是對的——只是各自對一半。

**做法**：優先用來源資料夾 ID 比對，找不到才退回文字比對。

---

## 4. 同款合併：一款一設計，代表列勾一次、整組生效

**問題**：同一款商品的不同顏色，原本各自跑一次完整流程。實際上設計師只需要做一份，換色是套版時的參數。

**現況**：**37 組主碼涵蓋 88 列，其中 55 品用同一份設計出兩個品牌。**

**踩到的坑**：改成「一組只做一份」之後，進度欄永遠卡在處理中——因為那個公式在數「已完成列數 vs 同組列數」，而一組只做一份時，`已完成 < 同組` 恆真。**改變「一列一份工」這個假設時，必須回頭掃所有數列數的公式。**

**放行的粒度**：勾選是**代表列勾一次、整組生效**；但清除的時候**整組都清**——那一欄有核取方塊的資料驗證，任何一列被人順手勾了都會讓匯出器重撿。

---

## 5. 匯出器連「已完成」的列也重新檢查

**問題**：設計師改完設計想重新出圖，但那一列的狀態已經是「完成」了。

**做法**：匯出器不再用狀態過濾，改成看勾選欄。這讓「再勾一次＝重出圖」能生效。

**連帶後果**：**勾選就必須在圖落檔後被清掉**，否則那一列會每 10 分鐘被重匯一次，永遠停不下來。這兩個決定是綁在一起的，不能只做一半。

---

## 6. 外部服務的同一個錯誤碼，有兩種意思

**問題**：匯出偶爾失敗，重試也失敗。

**根因**：外部儲存服務對「檔案還沒產生好」和「簽章連結已過期」回**同一個 HTTP 狀態碼**。前者該跨輪重試，後者該直接重建連結——但看錯誤碼分不出來。

**做法**：用簽章上的發出時間與有效期反推現在是哪一種。這兩種的處置完全相反，猜錯的成本是「一直重試一個永遠不會成功的東西」或「明明再等一下就好卻整批重建」。

> The same HTTP status code meant two opposite things: "not ready yet" (retry across rounds) and "signature expired" (rebuild the link). Telling them apart required reading the signature's issue time and TTL.

---

## 刻意不做的

- **不做全自動出圖。** 版面有品味判斷，機器排得出來排不對。理由見 README。
- **不把 ERP 建檔那一段放進存活檢查。** 它的漏跑偵測由備份主線負責，而那個檢查看的是「資料有沒有真的更新」，比「排程有沒有觸發」更貼近我們在意的事。兩邊都設＝同一件事發兩次警報。
- **不在解析失敗時當成健康。** 任何看不懂的欄位一律走 bad 或 skip，因為這整套系統要防的就是靜默故障。
